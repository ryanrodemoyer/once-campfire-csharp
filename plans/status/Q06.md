## What landed

- `parity/continuity/continuity.py`: Core client and response parsing engine with cookie jar, Rails/C# form extraction, and session handling.
- `parity/continuity/scenarios.py`: Seven continuity scenarios executed in both directions:
  1. `session_continuity`: Sign in on Server A, continue browsing authenticated pages on Server B, sign out across servers.
  2. `form_login_continuity`: Render unauthenticated login form on Server A, submit credentials to Server B.
  3. `form_message_continuity`: Render authenticated room message form on Server A, post message to Server B with per-form CSRF token.
  4. `form_profile_update_continuity`: Render profile form on Server A, submit profile update to Server B.
  5. `transfer_link_continuity`: Mint 4-hour session transfer link on Server A, redeem via PUT on Server B, continue authenticated session on Server B.
  6. `security_csrf_tamper_continuity`: Forged/tampered cross-server authenticity token is rejected with 422 Unprocessable Entity.
  7. `security_transfer_tamper_continuity`: Forged/tampered cross-server transfer token is rejected with 400 Bad Request.
- `parity/continuity/run`: Command-line executable harness supporting `--direction [both|rails-to-csharp|csharp-to-rails]`, `--scenario`, `--selftest`, and `--report`.
- `parity/continuity/test_continuity.py`: 11 offline unit tests covering cookie parsing, token extraction, mock scenario execution, and planted defect detection.
- `parity/continuity/Server.cs`: C# candidate server launcher hosting Kestrel over WebApp and SQLite database with synchronized clock support (`OffsetClock` reading `FAKETIME`).
- `parity/continuity/results.json`: Execution results demonstrating 14/14 scenarios passing across live Rails and C# servers.
- `parity/continuity/README.md`: Usage guide and scenario documentation.

## Notes for dependents

- The continuity harness can be re-run at any time against any pair of servers via `parity/continuity/run REF_URL CAND_URL`.
- Transfer tokens are 4-hour time-limited signed IDs; running against instances started with libfaketime / `--time` requires the candidate server clock to be synchronized via `FAKETIME` or `--time`.
