## What was built

- `src/Campfire.Web/Controllers/Messages/WriteController.cs`: `MessagesWriteController` with
  messages_controller.rb's chain (`set_room` except create, `set_message`,
  `ensure_can_administer` with `can_administer?(@message)`), create (room_not_found rescue,
  permitted params, `MessageLifecycle.Create`, `broadcast_create`, then
  `deliver_webhooks_to_bots`), show, edit, update (`update!` of body and client message id,
  `broadcast_replace_to … maintain_scroll`, `respond_to` html/json) and destroy
  (`broadcast_remove`). Pages render in the application layout; turbo streams render once and
  the broadcast reuses the bytes.
- `WriteRoutes.cs` binds the five actions; `WriteViews.cs` declares the templates and ports
  Lexxy 0.9's `rich_text_area` (the fallback it installs on Rails without editor adapters).
- `src/Campfire.Web/Views/messages/`: `create.turbo_stream`, `destroy.turbo_stream`, `edit`,
  `show`, `room_not_found`.
- `WriteServices.cs` gives `WebApp` what pages and writes need: `Assets`, `Storage`, `Seams`,
  `VapidPublicKey`.

## Notes for dependents

- **Server wiring (P lane / VS01):** set `WebApp.Assets`, `Storage`, `Seams` (I01's `JobRunner`
  as `Jobs`, RT's broadcaster) and `VapidPublicKey` when building the app; the message
  controllers throw without them. M03/M04 and other page controllers can use them too.
- **Broadcast renders have no CSRF tokens.** `ApplicationController.renderer` has no session,
  so a message rendered for a broadcast has token-less boost forms; create's response is that
  same render (Rails serves the cached fragment the broadcast wrote).
- **Turbo streams on the cable:** payloads are the turbo-stream tag JSON-encoded on
  `<room gid param>:messages`; the unread fanout is `{"roomId":…}` unencoded on
  `user_<id>_unreads`, in `room.memberships.pluck(:user_id)` order.
- **M10** (split from this task, see `plans/tasks.yaml`): messages with a file. Implement
  `MessagesWriteController.CreateWithAttachment(attributes, storedBody, ref create)` and
  `DestroyWithAttachment(message, ref destroy)` in `Controllers/Messages/Attachments*`; create
  continues with the broadcasts, webhooks and render once the hook returns the message.
- Updating `client_message_id` writes its own SQL (the message row, the room touch, the index
  after the commit), since Data has no operation for it.
- `MessagesControllerTests`' `MessagesApp` builds the app on the parity seed, with session
  cookies and CSRF headers for any session token; M06/M04 can reuse it.

## Known gaps

- **Attachments (M10):** creating a message with a file, replacing one by update, and destroying
  a message that has one answer 501 until M10 implements the hooks.
- **Fragment caching** (M02's gap): Rails serves a message's cached `_message` fragment, so a
  message first rendered by a broadcast shows token-less boost forms on later pages, and one
  first rendered in a request shows tokens. We always render, with tokens on pages. The replay
  leaves boost-form tokens out on both sides.
- **No-body message presentation:** a message without a body row (only a hand-made request
  makes one) presents as an empty `lexxy-content` div where Rails rescues to "". It's in M02's
  helper; reported on #43, and listed in `WriteControllerTests.KnownDifferences`.
