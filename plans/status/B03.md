## Notes for dependents

- The fragment cache (`MessageFragmentCache`) is process-local and starts cold each run. The cache stores rendered message HTML bytes keyed by message ID + updated_at + template version. It helps on repeated requests within the same process but doesn't skip the `MessageView` data loading (rich text, boosts, users, rooms queries). A read-path cache (checking before DB queries) would give larger gains.
- `PooledBufferWriter` uses `ArrayPool<byte>.Shared` with 64 KiB initial capacity. It replaces `new ArrayBufferWriter<byte>()` in the key controllers. Other controllers still use `ArrayBufferWriter` and would benefit from the same change.
- Server GC with DATAS is the .NET 10 default and is optimal. No GC configuration change was needed.
- The gzip buffer pool in `RackDeflater` uses `ArrayPool<byte>.Shared` instead of `MemoryStream`. The gain is within noise but the approach is less wasteful.

## Known gaps

- Read-path fragment cache (check cache before building MessageViews) — would give Go-port-level gains but requires architectural changes
- Reader pool optimization — 42% of CPU time waiting for readers at 16 concurrent clients; Rust port's reader-thread model is one approach
- Build profile tuning (LTO, single codegen unit) — not measured; the Rust port saw ~5-10% on app-bound routes
- Remaining controllers still use `ArrayBufferWriter<byte>()` instead of `PooledBufferWriter`
