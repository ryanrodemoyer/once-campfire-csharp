## What landed

- `parity/normalize/normalize.py` ports the Rust port's
  `reference-rust/parity/capture/normalize.ts` to Python's standard library. It turns a body into
  text that diffs like its DOM: one node per line, sorted attributes, collapsed whitespace and
  decoded entities, with canonical JSON. Values that legitimately differ between two servers
  become *typed* masks, so a token for the wrong record still differs:
  - `«csrf»`: a well-formed masked authenticity token.
  - `«sgid:Room#…»`: a decoded signed GlobalID.
  - `«signed_id:purpose:id:exp»`: decoded MessageVerifier output.
  - `«encrypted»`: MessageEncryptor output.
  - `«t-3600s»` and `«epochms-60s»`: timestamps decoded against the seed clock.
  - `«t:live»`: a time written during the run. With `--frozen-clock` it's decoded instead.
  - `«uuid»`, `«join_code»` and `«bot_key»`: values that are random by design.
  - Propshaft digests are masked too, unless `--keep-asset-digests` is passed.

  Unlike `normalize.ts`, it keeps CSRF fields (masked).
- `parity/replay/replay.py` generalizes
  `reference-rust/reference-tools/campfire/controllers_a/replay.py`. Each scripted session has
  one cookie jar per side, and every response pair is compared on five things:
  - `status`.
  - `header-shape`: the header names, less transport headers.
  - `header:NAME` values, masked. `X-Request-Id`, `X-Runtime` and `ETag` are compared only by
    presence. HTTP dates are decoded.
  - `set-cookie`: each cookie's name, attributes and value type. A deletion is recognized from
    its attributes.
  - `body`: the normalized body.
- `parity/replay/families/` holds the route families, named after controllers so a feature task
  can gate only its own routes (`parity/replay/run --list`):
  - Read-only: `sessions:anon`, `account:read`, `users:read`, `rooms:read`, `messages:read`,
    `searches:read`, `pwa`.
  - Writing: `sessions`, `join`, `account`, `bots`, `users`, `rooms`, `messages`, `bot_api`,
    `searches`.
  - Other seeds: `crowd` (on the `crowd` seed) and `first_run` (on the `first_run` seed).
- `parity/replay/run REF CAND [--family A,B | group:] [--seed] [--read-only] [--report FILE]
  [--capture DIR]` exits 0 when everything matched, 1 on any difference and 2 when a scenario
  couldn't run.
- `parity/replay/defects.py` is a proxy that plants one known defect in front of a server:
  - `missing-class:NAME`
  - `page-size:±1`
  - `status:PATH=CODE`
  - `header:NAME`
- `parity/replay/selftest REF OTHER` runs Ruby vs Ruby, then replays through every planted defect
  and requires each one to be caught as the expected kind of difference.
- Offline unit tests: `python3 -m unittest discover -s parity/normalize -p 'test_*.py'` (18 tests)
  and `python3 -m unittest discover -s parity/replay -p 'test_*.py'` (12 tests). Both are green.

## Notes for dependents

- Gate a feature with `parity/replay/run REF CAND --family <yours>` against fresh instances on the
  same seed. Read-only families can share instances. Writing families need a fresh copy of the
  seed, because each family's writes go to both sides.
- Add routes by adding a scenario to the family module that owns the controller, or a new module
  imported in `families/__init__.py`. Call `run.compare(name, pair.get(...))` on every response.
- Sign-in is rate limited per IP, so give each scenario its own client IP (`run.pair(ip)` /
  `run.signed_in(user, ip)`).
- If the host has no Docker, the native runtime needs Ruby matching `reference/.ruby-version`
  (3.4.10), plus `rsync`, `redis-server` and libfaketime.
