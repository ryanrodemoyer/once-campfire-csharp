## Notes for dependents

- **Seams** (`src/Campfire.Data/Events/`):
  - `IBroadcaster.Broadcast(stream, payload)` = `ActionCable.server.broadcast`. Lifecycle never
    calls it: every broadcast in the reference comes from controllers/jobs (`broadcast_create`,
    `broadcast_remove`, the `user_<id>_unreads` fanout). M05/RT03 render and broadcast.
  - `IJobQueue.Enqueue(Job)` with `PushMessageJob(RoomId, MessageId)`, `WebhookJob(BotId,
    MessageId)`, `RemoveBannedContentJob(UserId)` (`ClassName`, `ArgumentIds`). **I01:** Lifecycle
    already calls it at the reference's moment, so enqueue immediately; do not defer to a commit
    (Rails doesn't; deferring changes `user_ban`'s vector).
  - `IConnectionRevoker.Disconnect(userId, reconnect)` = `remote_connections.where(current_user:)
    .disconnect`. Not transactional, as in Rails.
- **Lifecycle** (`src/Campfire.Data/Lifecycle/`): static operations over `WriteTransaction`, so a
  caller's transaction is the Rails transaction they join; after-commit work goes through
  `WriteTransaction.AfterCommit`.
  - `MessageLifecycle.Create(tx, seams, roomId, creatorId, clientMessageId, bodyHtml?, plainTextBody, now)`;
    then `DeliverWebhooksToBots(session, jobs, room, message, mentionedUserIds)` after the commit
    (register it with `tx.AfterCommit` after Create, as the test does). `UpdateBody`, `Destroy`.
  - `BoostLifecycle.Create/Destroy` (take the message and its `plainTextBody` for the re-index).
  - `UserLifecycle.Create`, `CreateBotAsync(database, ...)` (two transactions), `Deactivate`,
    `Ban` (throws `RecordInvalidException` and rolls back on a non-public session address), `Unban`.
  - `MembershipLifecycle.Destroy`, `Revise`, `RevokeFromAsync(database, ...)`.
  - Callers render `plainTextBody` (`body.to_plain_text.presence || attachment filename || ""`)
    and the mentioned user ids from the rich text (R lane); Data doesn't parse rich text.
  - `MessageSearchIndex` holds the three FTS statements of message/searchable.rb; D04 may move
    them into `Search/` and Lifecycle can call that instead.

## Known gaps

- Attachments: `create_with_attachment!` with a file (blob/attachment rows, upload after commit,
  `process_attachment`) and destroying a message with an attachment (`purge_later`) aren't in
  Lifecycle. Per has_one_attached's position in message.rb, the attachment's save runs before the
  rich text's and its upload is the first after-commit step. M05/S-lane add them with a vector.
- Rails merges repeated `touch_later`s of one record within a transaction into one UPDATE; each
  Lifecycle operation touches on its own, so two operations in one transaction touch twice (same
  timestamps, an extra statement). No reference flow does that.
- `RemoveBannedContentJob`'s body (destroy each message, then `broadcast_remove`) is I01/M05's,
  built from `MessageLifecycle.Destroy`.
