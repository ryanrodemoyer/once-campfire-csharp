## Notes for dependents

- `src/Campfire.Data/Checkpoint/SqliteWalCheckpoint.cs` ports the Rails module as an instance:
  `Start(interval)`, `Stop(timeout)` (throws `SqliteWalCheckpoint.StopTimeoutException`),
  `Checkpoint()`, `Tick()`. The constructor takes the database path, the lock path and an optional
  `warn` callback, where Rails logs.
- `FileLock` is internal. It is a non-blocking exclusive `flock(2)`, taken through `open(2)` and
  `libc` `flock`/`close`. Opening the lock file with `File.Open` would not work: .NET takes its own
  `flock` on every file it opens, so a held lock would fail the open instead of reporting busy.
  Linux and macOS only.
- `src/Campfire.Data/Checkpoint/WriterCheckpointFallback.cs` is called by `SqliteDatabase`'s writer
  thread after every commit (see the difference below).
- `ServerCommand.RunAsync` starts the checkpointer after `PrepareDatabase` and stops it before
  `Commands.Close`, so the flock and the connection are released before the database closes.

## Known gaps

- **Difference from the reference: the writer fallback.** The card asks for "the writer fallback that
  bounds WAL growth". Rails' `sqlite_wal_checkpoint.rb` at edbc779 has no writer-side checkpoint
  beyond the best-effort exit checkpoint. The measurements above show why this port needs one: with
  a steady stream of commits, a contender's PASSIVE checkpoint never finishes between two commits, so
  the WAL never restarts. `WriterCheckpointFallback` checkpoints on the writer when the WAL is over
  4 MiB, which is SQLite's default `wal_autocheckpoint` of 1,000 pages. It runs only when the
  contender has fallen behind. Without an entry under "Known differences" in `README.md` (not in this
  task's `owns`), this is an undocumented difference from Rails. The owner should decide whether to
  keep it and list it there.
- The short-lived CLI commands (`campfire prepare`, `campfire backup`) don't start a contender or
  the exit checkpoint. Rails' initializer runs in every process, rake tasks included. Picking this up
  needs a checkpointer lifetime in `Commands`; left out here because `Commands.Close` has no handle
  for one.
- The exit checkpoint is installed by `Start`, so it covers only the server process.
- `FileLock` uses libc `flock` and `open`, which exist on Linux and macOS. Windows isn't supported;
  the server runs in Linux containers.
