## Notes for dependents

- **Running the production media check**: `tests/Campfire.Server.Tests/ProductionImage/run.sh`
  (optional: an image name, then `-- <dotnet test args>`). It builds the root `Dockerfile` as
  `campfire-csharp:production-media`, so it takes the host architecture. The test skips unless
  `CAMPFIRE_PRODUCTION_URL` is set, which only this script does, so `bin/check` never runs the
  container.
- **Wiring**: the libraries live in the runtime stage, so the `ARG` pins for `LIBVIPS_PACKAGE_VERSION`,
  `FFMPEG_PACKAGE_VERSION` and `FFMPEG_VERSION_LINE` are declared at the top of the root `Dockerfile`
  and repeated in its runtime stage, as the toolchain's `media` stage does.
- **Shape of the test**: the reference's routes and fixtures only, with no hand-written expected
  bytes. Expected bytes come from `vectors/storage/` through `StorageVectors`. The project
  `Campfire.Server.Tests` now references `tests/Campfire.Vectors`.

## Known gaps

- **Not in CI.** No CI job runs `tests/Campfire.Server.Tests/ProductionImage/run.sh`. It needs
  Docker and the image build, and F03's workflow (`.github/workflows/`) isn't P07's to add. Until then
  it runs on demand, as P02's `docker/toolchain/media-tests` does.
- **arm64 not run.** The check ran on amd64 only. On arm64 the libvips image variant bytes match, but
  the video poster is ffmpeg output and, per P02 (`docker/toolchain/README.md`), isn't byte-identical
  across architectures, so `An_uploaded_video_gets_the_reference_poster` would need the same arm64
  exclusion `docker/toolchain/media-tests` applies. Left for whoever runs arm64, since it needs a
  QEMU run.
