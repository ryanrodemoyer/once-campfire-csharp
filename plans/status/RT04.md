## Acceptance evidence

- [x] Named subscribe -> revoke -> deliver -> reconnect test passes for every channel including Turbo
  - `RevocationTests.Subscribe_revoke_deliver_reconnect(channel, revoke)` runs 27 named cases.
    That is every registered channel (`ApplicationCable::Channel`, `HeartbeatChannel`,
    `PresenceChannel`, `ReadRoomsChannel`, `RoomChannel`, `RoomMessagesChannel`,
    `TypingNotificationsChannel`, `UnreadRoomsChannel` and `Turbo::StreamsChannel` on the
    sidebar's `<user gid>:rooms` stream) times each revocation: membership removal
    (`MembershipLifecycle.RevokeFromAsync`), `UserLifecycle.Deactivate` and `UserLifecycle.Ban`.
    Every case goes through the real `CableConnectionRevoker` over Kestrel. Each case does this:
    1. It subscribes and checks that a publication reaches the subscriber.
    2. It revokes, then publishes at once. The old socket's only events are
       `{"type":"disconnect","reason":"remote","reconnect":true|false}`, the 1000 close and
       the end, so the publication made while it was closing never arrives. The broadcasting
       then has 0 receivers.
    3. It reconnects. After a membership removal the room-carrying channels are rejected and
       nothing reaches them, while the user's own streams (reads, unreads, Turbo user rooms,
       heartbeat, base) confirm and deliver. After a deactivation or a ban the connection gets
       `{"type":"disconnect","reason":"unauthorized","reconnect":false}`.
  - `Removing_a_membership_keeps_the_rooms_the_user_still_has`: after a reconnect, the rooms
    the user is still in confirm on `RoomChannel` and `RoomMessagesChannel`. The stock
    `Turbo::StreamsChannel` rejects the lost room's signed `:messages` name. The unread fanout
    (authorized per publication, since it plucks the members at the time) reaches the user for
    the room they kept and not for the one they lost.
  - `Only_the_revoked_users_connections_are_closed` (one case per revocation): both of the
    revoked user's sockets close. Another member on the same room stream keeps receiving.
  - `A_connection_opened_while_the_revocation_is_in_its_transaction_is_refused` (deactivation
    and ban): a connection opened while the revoking transaction is still open, so its
    session is the last commit, gets no welcome. It is refused once the transaction commits.
    With the guard switched off (`SettleAsync` returning early), both cases fail with a welcome.
    That was checked locally and reverted.
  - `A_revocation_that_rolls_back_still_disconnects_and_lets_the_user_back_in`: the disconnect
    happens at once and isn't undone, as in Rails. The user can connect again afterwards.
  - `Connections_of_users_never_revoked_skip_the_guard`.
- `bin/check` on this branch: plan validate, format, Release build and every test project
  green. Cable: `Passed: 94, Failed: 0`, which is 59 existing tests plus the 35 in
  `Campfire.Cable.Tests.Revocation`.

## Notes for dependents

- Wire the cable server and the domain seams like this (P01, which mounts `/cable`):

  ```csharp
  var guard = new RevocationGuard(database);
  var server = AppChannels.Register(
      CableServer.Builder(config, guard.Authenticate(new SessionCookieAuthenticator(database, keys))),
      database, keys).Build();
  var seams = new DomainSeams(broadcaster, jobs, guard.RevokerFor(server));
  ```

- `CableConnectionRevoker.Disconnect(userId, reconnect)` implements `IConnectionRevoker`. It
  sends `remote_connections.where(current_user:).disconnect(reconnect:)` on the user's internal
  channel (`action_cable/gid://campfire/User/<id>`). When it returns, every connection of that
  user has stopped sending, so no later publication reaches them. Closing then unsubscribes
  every channel, which means `PresenceChannel#absent` runs and raises for a membership that is
  gone, as `NoMethodError` does in Rails, and the error is logged.
- `RevocationGuard` closes a gap Rails has. Deactivation and ban disconnect inside their
  transaction (D03 keeps the Rails order). A connection that authenticates before that
  transaction commits would see the old session and stay open. After a revocation, the next
  connection for that user waits for one empty write, which runs after the revoking
  transaction, and then authenticates again. Users who were never revoked skip the extra step.
  The pending entry is cleared by that connection, using a sequence number so that a later
  revocation is never forgotten.
- Per-publication authorization works through what is authorized at publish time. Room
  streams are authorized when the subscription is made, and revocation closes the connection
  before any later publication. The unread fanout plucks the current members on every
  publish.
