## Acceptance evidence

- [x] Backup during a write load restores to a consistent DB that both C# and Rails boot
  - **What `campfire backup` does** (`src/Campfire.Server/Backup/Backup.cs`): it ports
    `reference/script/admin/prepare-backup`. The live database is opened as Active Record opens
    it (`SqliteConnections.Open`: WAL plus the adapter's pragmas), and the destination as a plain
    `SQLite3::Database.new` would be. Then one `sqlite3_backup_step(-1)` and `finish`
    (Microsoft.Data.Sqlite's `BackupDatabase`) write `storage/backups/<env>.sqlite3`. Like Rails,
    it creates `storage/backups` and the database's directory. Exit codes: 0 on success. On a
    database it can't read, 1 with `campfire backup: <SQLite message>`.
  - **In CI** (`tests/Campfire.Server.Tests/Backup/BackupTests.cs`):
    `Backup_during_a_write_load_restores_to_a_consistent_database` takes a copy of D01's Rails
    fixtures database. A second connection commits two-message transactions in a loop while
    `campfire backup` runs, and the writer keeps going afterwards.
    - The backup holds a whole number of transactions: an even count of rows, at least the 50
      transactions committed before the backup, and no more than had committed when it finished.
    - The test then runs `reference/hooks/post-restore` itself, with `/rails` moved to the test
      root. Afterwards no `-wal` is left, the row count matches, `integrity_check` is `ok`,
      `foreign_key_check` is empty, and `campfire db:prepare` boots on the result with exit 0.
    - Other tests check that a quiescent backup matches the source table for table, that the
      file is named after `RAILS_ENV`'s database, that a second run replaces the first backup,
      and that an unreadable database exits 1 with SQLite's message.
  - **Across processes, with both apps booting the result** (run in this session):
    - The source was `tests/Campfire.Data.Tests/Oracle/parity-seed.sqlite3`, the parity seed's
      database, as `storage/db/production.sqlite3`. A separate Ruby process (the `sqlite3`
      2.9.6 gem, WAL, busy_timeout 5000) committed two-message transactions nonstop.
    - The published `campfire backup` ran three times while it wrote. The writer was at 2000,
      3200 and 4300 transactions when the three backups finished, and reached 22,200 in all.
      Every run exited 0.
    - The reference's `post-restore` (paths rewritten to the scratch root) restored the last
      snapshot: 8,012 load rows (4,006 whole transactions), `integrity_check` `ok`. The one
      `foreign_key_check` row (message 933434637 → users) is already in the seed.
    - **Rails**: Ruby 3.4.10 was built from the `v3_4_10` tag, then the native reference runtime
      (`PARITY_RUNTIME=native parity/bin/reference build`). `parity/bin/reference up --seed
      p04-restored`, with that file as the seed's database, booted `bin/boot` (Thruster, then
      `db:prepare` and Puma): `/up` → 200 and `/session/new` → 200 `<title>Sign in</title>`.
      `bin/rails runner` in that instance printed `8012`, `ok` and `needs_migration? == false`.
    - **C#**: `campfire server` on the same file ran `db:prepare` and served. `/up` and
      `/session/new` are routed but still answer the router's 501 stub until A08 and A01 bind
      their handlers (see P01).
  - `bin/check` passes. It also passed three runs in a row before `main` was merged in, to check
    that the load test isn't flaky.

## Notes for dependents

- The image needed no changes. P01's Dockerfile already installs `/hooks/pre-backup`
  (`cd /rails && campfire backup`) and copies `reference/hooks/post-restore` unchanged as
  `/hooks/post-restore`. The backup lands where that script reads it:
  `/rails/storage/backups/<env>.sqlite3`. So `hooks/` stays empty. A port-owned copy of the
  hooks would only duplicate the Dockerfile's.
- `Commands.CreateBackup(ServerSettings)` is public and returns the backup's path, for B05 or
  anything else that wants a snapshot in-process.
- The backup is a single `step(-1)`, as in Rails. It reads one WAL snapshot, so writers in other
  connections and processes carry on while it runs. Nothing is retried on `SQLITE_BUSY`, and Ruby
  doesn't retry either.
