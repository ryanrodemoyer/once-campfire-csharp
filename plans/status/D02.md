## Notes for dependents

- **Records** (`Campfire.Data.Records`): one immutable `sealed record` per table: `Account`
  (+ `AccountSettings` for `has_json`), `User` (`UserRole`, `UserStatus`), `Session`, `Room`
  (`RoomType`, `RoomTypes.ClassName/FromClassName`), `Membership` (`Involvement`,
  `Involvements.Name/FromName`), `Message`, `Boost`, `Ban`, `Search`, `PushSubscription`,
  `Webhook`, `ActionTextRichText`, `ActiveStorageBlob`, `ActiveStorageAttachment`,
  `ActiveStorageVariantRecord`. `RecordTypes` and `AttachmentNames` hold the polymorphic values.
  Each record has an internal `Columns` list and `Read`/`ReadAt(reader, offset)` for joins.
  Model methods that need no database are on the records (`User.BotKey/Initials/Title/CanAdminister`,
  `Membership.IsConnected(now)`, `Session.NeedsActivityRefresh(now)`, `Account.GenerateJoinCode`).
- **Queries** (`Campfire.Data.Queries`): static classes named after the tables (`Users`, `Rooms`,
  `Memberships`, `Messages`, `Boosts`, `Bans`, `Searches`, `Sessions`, `PushSubscriptions`,
  `Webhooks`, `RichTexts`, `Blobs`, `Attachments`, `VariantRecords`, `Accounts`). Every method takes
  a `SqliteSession` (`tx.Session` for writes) and, when it writes a time, an explicit `now`: pass
  `TimeProvider.GetUtcNow()` once per request so callbacks agree. Each method cites the Rails
  scope it is; add new ones next to them. Updates take the record and write only what changed,
  with `updated_at`, and return the record unchanged (same instance) when nothing did, like
  `update!`. `Change<T>?` distinguishes "not assigned" from "set to NULL".
- **SQL mirrors Rails' SQL** where order can tie (e.g. `ORDER BY LOWER(name)`, unqualified, and the
  join order of `Rooms::Direct.find_for`), so SQLite breaks ties the way it does for Rails.
- **`insert_all`** (`Memberships.GrantTo/GrantRoomsTo`) lets SQLite stamp
  `STRFTIME('%Y-%m-%d %H:%M:%f', 'NOW')` and skips existing members (`ON CONFLICT DO NOTHING`), as
  Rails does.
- **No callbacks here.** D03 composes these queries into Rails' callback order:
  `Rooms::Open` granting all active users after save, `User` granting open rooms after create,
  `Room#receive` (`Memberships.MarkUnread` + push), touches (`Rooms.Touch`, `Messages.Touch`),
  `Membership` destroy resetting connections (`Memberships.RevokeFrom` returns what it deleted),
  `deactivate` and `ban`. `Rooms.Delete` and `Messages.Delete` delete only their own row.
- **Never call `SqliteDatabase.WriteAsync` from inside a write**: it waits for itself (a test did
  this and hung).
- **Not here**: validations of user input (`Ban#ip_address_is_public` for A04,
  `Push::Subscription#validate_endpoint_url` for A07), `Search.record` (D04), pagination (D05),
  rich text rendering and `plain_text_body` (R lane), `FirstRun` (A01).

## Known gaps

- `queries.json` and `parity-seed.sqlite3` come from the native runtime (Ruby 3.4.10, host libvips
  and ffmpeg), as V02's hashes did. Only media bytes depend on the runtime, and the database dump
  matches `SEED.sha256`. Regenerate both with the commands at the top of `queries.rb` after a
  Docker-built seed changes `SEED.sha256`.
- A datetime column that Active Record can't parse throws `InvalidDataException` on read (Rails
  reads nil); nothing writes such text. An unknown STI `type` throws as Rails' `SubclassNotFound`
  does. An unknown involvement reads as null, as in Rails.
