## Notes for dependents

- **Running the golden set**: `docker/toolchain/media-tests` (defaults to the host
  architecture; `both` runs each in turn; `arm64` needs
  `docker run --privileged --rm tonistiigi/binfmt --install arm64` first on an amd64 host).
  Extra arguments after `--` pass through to `dotnet test`, e.g.
  `docker/toolchain/media-tests both -- --logger "console;verbosity=detailed"`.
- **The production image wiring is left to P01's owner** (`Dockerfile`, issue #26): its runtime
  stage installs the same two pinned packages next to its `ca-certificates`; the lines are in
  `docker/toolchain/README.md`. Until then the production image cannot make variants or
  previews; the comment on issue #26 has the request. The `media` stage of
  `docker/toolchain/Dockerfile` is that runtime set on its own, for reference.
- **Why binary packages instead of building from source** (the Go/Rust route): the same .debs as
  the reference image are a stronger oracle than a trimmed rebuild, nothing is left out for
  Campfire to reach later (the ports' trimmings exclude loaders Campfire could reach with a
  changed config), and apt's signed indexes do the checksum pinning. The trade-off: if Debian
  trixie publishes newer media packages, the pinned install fails the build rather than
  silently drifting — then regenerate the vectors (a rebuilt reference image would drift the
  same way), or pin via snapshot.debian.org.
- **CI**: a job running `docker/toolchain/media-tests both` per PR would gate the toolchain
  continuously; the workflow (`.github/workflows/`, F03's, issue #4) is not P02's to add — the
  comment on issue #4 has the request. The versions' own gate still runs wherever
  `CAMPFIRE_REQUIRE_MEDIA_VECTORS=1` is set: the image.
- The .NET SDK comes over whole from `mcr.microsoft.com/dotnet/sdk:10.0` (Ubuntu; Microsoft
  ships no Debian .NET 10 image) with `libicu76` added: the SDK's own host needs ICU, while the
  app and tests don't (`InvariantGlobalization`, `Directory.Build.props`). An SDK that stops
  satisfying `global.json` fails every `dotnet` command inside the image, so it can't drift
  silently.

## Known gaps

- The production image (the root `Dockerfile`) does not yet install the media packages; that
  edit belongs to P01's `owns`, requested on issue #26. Media processing is unavailable in the
  production image until then.
- No CI job builds the toolchain image or runs the golden set per PR (requested on issue #4,
  F03's `.github/workflows/`). Until then the gate runs only on demand, locally.
- arm64 evidence is QEMU emulation on the amd64 swarm host, not native hardware; the binaries
  are Debian's own arm64 .debs. Image variant bytes match the (amd64-made) vectors on both
  architectures; the video preview bytes differ between architectures — this is expected with
  binary ffmpeg packages and is documented in `docker/toolchain/README.md`. Native arm64 would
  be faster but is not available here.
